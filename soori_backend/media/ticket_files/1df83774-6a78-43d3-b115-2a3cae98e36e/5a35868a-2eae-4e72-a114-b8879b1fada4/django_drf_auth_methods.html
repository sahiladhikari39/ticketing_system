Authentication in Django REST Framework (Function Based Views)
This guide uses function-based views only (no class-based views) and includes custom register and custom login code for every authentication method. Each method trades off between security, scalability, and ease of implementation.

Session Authentication

Custom @api_view register and login using Django's session framework. Cookie-based auth for browser clients.

Token Authentication

Custom @api_view register and login. Generates a DRF token on login and returns it in the response.

JWT Authentication

Custom @api_view register and login. Issues access + refresh tokens on successful login.

PEM / mTLS Authentication

Custom @api_view register that stores public keys. No login endpoint — auth is per-request via signature.

Rule of thumb: Use Session for server-rendered pages, Token for simple APIs, JWT for scalable SPAs/mobile apps, and PEM/mTLS for service-to-service or high-security environments.

Uses Django's built-in session framework. After custom login, the server creates a session record and sends a sessionid cookie. Every subsequent request includes this cookie automatically.

Custom Login (Function Based View)
# settings.py REST_FRAMEWORK = { 'DEFAULT_AUTHENTICATION_CLASSES': [ 'rest_framework.authentication.SessionAuthentication', ], 'DEFAULT_PERMISSION_CLASSES': [ 'rest_framework.permissions.IsAuthenticated', ], } # views.py — Custom Login (Function Based View) from django.contrib.auth import authenticate, login from rest_framework.decorators import api_view, permission_classes from rest_framework.response import Response from rest_framework.permissions import AllowAny from rest_framework import status @api_view(['POST']) @permission_classes([AllowAny]) def login_view(request): username = request.data.get('username') password = request.data.get('password') if not username or not password: return Response({ 'error': 'Please provide both username and password.' }, status=status.HTTP_400_BAD_REQUEST) user = authenticate(request, username=username, password=password) if user is not None: login(request, user) return Response({ 'message': 'Login successful', 'user_id': user.id, 'username': user.username, }, status=status.HTTP_200_OK) else: return Response({ 'error': 'Invalid credentials' }, status=status.HTTP_401_UNAUTHORIZED) # views.py — Custom Logout from django.contrib.auth import logout @api_view(['POST']) def logout_view(request): logout(request) return Response({ 'message': 'Logout successful' }, status=status.HTTP_200_OK) # views.py — Protected endpoint (Function Based View) @api_view(['GET']) def profile_view(request): return Response({ 'username': request.user.username, 'email': request.user.email, }) # urls.py from django.urls import path from .views import register_view, login_view, logout_view, profile_view urlpatterns = [ path('register/', register_view, name='register'), path('login/', login_view, name='login'), path('logout/', logout_view, name='logout'), path('profile/', profile_view, name='profile'), ] # Client usage # 1. Register # curl -X POST http://api.example.com/register/ \ # -H "Content-Type: application/json" \ # -d '{"username":"john","password":"secret123","password2":"secret123","email":"john@example.com"}' # 2. Login (sets session cookie) # curl -X POST http://api.example.com/login/ \ # -c cookies.txt -H "Content-Type: application/json" \ # -d '{"username":"john","password":"secret123"}' # 3. Access protected endpoint # curl http://api.example.com/profile/ -b cookies.txt # 4. Logout # curl -X POST http://api.example.com/logout/ -b cookies.txt
Pros: Simple, battle-tested, CSRF protection built-in, easy logout (server invalidates session).
Cons: Requires cookies (not ideal for mobile/native apps), session DB lookup on every request, harder to scale across multiple servers without shared session storage.

Login (get token) # curl -X POST http://api.example.com/login/ \ # -H "Content-Type: application/json" \ # -d '{"username":"john","password":"secret123"}' # Response: {"token":"9944b09199c62bcf9418ad846...","user_id":1,...} # 3. Pros: Simple to set up, works with any HTTP client, no cookies needed, easy to test with curl.

JWT Structure: header.payload.signature — Base64Url encoded. The payload contains claims like user_id, exp (expiry), iat (issued at).
Pros: Stateless (no DB lookup per request), scalable, short-lived access tokens reduce damage from theft, refresh token rotation improves security, industry standard.
Cons: Cannot revoke access tokens before expiry (unless using a blacklist), slightly more complex client logic (handling refresh), token size is larger than simple tokens.
PEM / mTLS Authentication (Function Based Views)
PEM (Privacy Enhanced Mail) files contain cryptographic keys (RSA/ECDSA). In DRF, PEM-based auth means either: (1) Client Certificate Authentication (mTLS) where the client presents a certificate, or (2) Custom RSA key-pair auth where the client signs requests with a private key and the server verifies with a public key. All views are function-based.
Method A: Client Certificate (mTLS)
The server requests a client certificate during the TLS handshake. Nginx/Apache validates the certificate, then passes a header to DRF identifying the authenticated client.

# Nginx config (reverse proxy for mTLS) server { listen 443 ssl; ssl_certificate /etc/nginx/ssl/server.crt; ssl_certificate_key /etc/nginx/ssl/server.key; ssl_client_certificate /etc/nginx/ssl/ca.crt; ssl_verify_client on; location / { proxy_pass http://django_app; proxy_set_header SSL_CLIENT_VERIFY $ssl_client_verify; proxy_set_header SSL_CLIENT_DN $ssl_client_s_dn; } } # authentication.py — RSA signature verification import base64 from cryptography.hazmat.primitives import hashes, serialization from cryptography.hazmat.primitives.asymmetric import padding from rest_framework import authentication, exceptions from .models import User class RSASignatureAuthentication(authentication.BaseAuthentication): def authenticate(self, request): api_key = request.headers.get('X-Api-Key') signature = request.headers.get('X-Signature') if not api_key or not signature: return None try: user = User.objects.get(api_key=api_key) except User.DoesNotExist: raise exceptions.AuthenticationFailed('Invalid API key') if not user.public_key_pem: raise exceptions.AuthenticationFailed('No public key registered') public_key = serialization.load_pem_public_key( user.public_key_pem.encode('utf-8') ) body = request.body try: public_key.verify( base64.b64decode(signature), body, padding.PKCS1v15(), hashes.SHA256() ) except Exception: raise exceptions.AuthenticationFailed('Invalid signature') return (user, None) # authentication.py — mTLS Client Certificate class ClientCertificateAuthentication(authentication.BaseAuthentication): def authenticate(self, request): verify = request.META.get('HTTP_SSL_CLIENT_VERIFY') if verify != 'SUCCESS': return None client_dn = request.META.get('HTTP_SSL_CLIENT_DN', '') cn = self._extract_cn(client_dn) try: user = User.objects.get(client_cert_cn=cn) except User.DoesNotExist: raise exceptions.AuthenticationFailed('No such user') return (user, None) def _extract_cn(self, dn): for part in dn.split('/'): if part.startswith('CN='): return part[3:] return dn # Pros: Highest security — no shared secrets over the wire, non-repudiation (proof of origin), no token expiry management, excellent for IoT and microservices.
Cons: Complex setup (certificate infrastructure), key management overhead, harder to rotate keys, not suitable for browser-based SPAs, requires cryptography knowledge.

Decision Guide
  • 1
    Browser + Django templates? → Session Authentication
  • 2
    Simple API with few clients? → Token Authentication
  • 3
    SPA / Mobile app with scale needs? → JWT Authentication
  • 4
    Service-to-service, IoT, or high-security? → PEM / mTLS
  • 5
    Multiple client types? → Combine: Session for web, JWT for API consumers.
